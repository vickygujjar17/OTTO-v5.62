564: feature — Near-Edge Pullback entry geometry + price-crossing guard

RATIONALE

  v5.63 left the entry offset and the stop distance as the SAME expression:

      entry = nearEdge +/- slDist            (slDist = blockHeight + 0.5*ATR)
      stop  = entry  -/+ slDist

  Because the far edge is exactly one blockHeight past the near edge, that
  collapsed to "entry 0.5*ATR past the far edge, stop exactly ON the near
  edge". Two DIFFERENT concepts -- how far out to enter, and how much risk to
  take -- were welded to one number, so the entry could not be widened without
  silently widening the stop, its lot size, every 1R trail milestone and every
  basket seed.

  v5.64 separates them:

      entry = nearEdge +/- (blockHeight + 1.0*ATR)    <- its OWN coefficient
      stop  = entry  -/+ slDist                       <- UNCHANGED risk

  The entry now sits a full 1.0*ATR beyond the far edge the breakout crosses
  (was 0.5*ATR), i.e. one further 0.5*ATR out than any previous build. Risk
  per unit is IDENTICAL to v5.63 by construction: entry<->stop is still
  exactly slDist.

  A setup the market has ALREADY run through is now stale rather than a
  resting level: the move the geometry was waiting for happened without this
  order, so the only fill left is a chase at market. v5.64 refuses to arm
  those (IsEntryCrossed), which is the price-crossing guard.

    double slDist = b.blockHeight + (0.5 * atr);
    return ... ? (b.bottom + slDist) : (b.top - slDist);
  becomes
    double pullback = b.blockHeight + (1.0 * atr);

    (stop 0.5*ATR INSIDE the zone when ATR < 2*blockHeight), with an explicit
    "do NOT restore the stop onto an edge" note, because restoring it requires
    changing slDist -- the one number this release must not move.

  COttoOrderManager.mqh -- CalcEntryPrice() rewritten to the SAME arithmetic
    Twin contract kept character for character (the probe asserts it). The
    rationale now says the pair must agree because a caller would judge a
    different entry from the order's, and records that the pair is DORMANT
    (its last reader, the Front-Run veto, was deleted in v5.63) -- which is

  COttoOrderManager.mqh -- CalcSLDistance() comments only, body untouched
    Still blockHeight + 0.5*ATR. The header now explains that this is
    deliberately INDEPENDENT of the entry offset and why lengthening it to
    "fix" the stop-inside-zone case would change every lot size and milestone.

  COttoOrderManager.mqh -- NEW IsEntryCrossed(block, entryPrice)
    The exact negation of the virtual trigger test, on the same side
    (ask for a LONG, bid for a SHORT) so the two cannot disagree by a spread:

        triggers : isLong ? (ask < triggerPrice) : (bid > triggerPrice)
        crossed  : isLong ? (ask >= entryPrice)  : (bid <= entryPrice)

    Placed next to GetPriceBoundaryBuffer(). Returns true for entryPrice<=0
    ("no geometry, nothing to wait for").

  COttoOrderManager.mqh -- original GATE wiring, with two scoping conditions
    Called from PlaceOrArmOrder() AFTER entryPrice/slDist are computed and
    BEFORE the hybrid router. TWO conditions, both load-bearing:

      1. InpEntryStyle != ENTRY_MIDPOINT. A midpoint entry sits INSIDE the
         zone, hence behind the market by construction; the bare test would be
         true on every healthy midpoint setup and retire that style wholesale.
      2. BEFORE the router, not inside its virtual branch. For a FRONT_EDGE
         setup, priceValid (legal to REST) ALREADY implies crossed -- a LONG
         entry 1.0*ATR above the far edge can only sit below the bid once the
         market has run through it. Testing only in the virtual branch would
         let the router REST a chasing limit below market for exactly the
         setups the guard exists to refuse.

    On a hit the block is LATCHED (hasPlacedOrder = true + SetBlockAt) and NOT
    vetoed: the setup is SPENT, not invalid. Without the latch
    PlaceOrdersForArmedBlocks() would re-log the rejection every tick.

    CONSEQUENCE, accepted and documented in place: with the guard live, ROUTE A
    (physical resting limit) is unreachable for ENTRY_FRONT_EDGE. That is
    correct rather than a regression -- a FRONT_EDGE entry that is legal to
    rest is by definition one the market already ran through -- and the virtual
    cross was already the ordinary path for this style. ROUTE A remains live
    for ENTRY_MIDPOINT.

  COttoOrderManager.mqh -- GetOrderTypeForBlock() UNCHANGED (still LIMIT)
    Deliberately not switched to BUY_STOP/SELL_STOP. That would re-open the
    physical route for the pullback entry, but it changes the EXECUTION MODEL,
    not the geometry, so it is not bundled into a geometry release. The
    reasoning is recorded in the function so the next reader does not "fix"
    it by accident.

  COttoOrderManager.mqh -- CheckVirtualTriggers() header rewritten
    The inverted cross test is UNCHANGED (the FIX (v5.57) predicate is
    character-for-character the same). The header now states the v5.64 ROLE
    explicitly: still the PRIMARY armed-to-filled path, not a fallback. The
    guard only refuses to ARM a crossed setup, so every setup that does arm is
    still waiting for this cross, and a freshly armed order can never fire on
    the tick it armed.

  COttoOrderManager.mqh -- OpenReversalPosition() documented as guard-exempt
    NOT silently edited. The SAR flip enters at the live ask/bid and never
    prices off CalcEntryPrice, so IsEntryCrossed() would be true on every call
    and would retire the reversal entirely. The exemption is stated in the
    source with that exact reasoning; its stop still comes from CalcSLDistance
    and so keeps the unchanged 1R basis.

  COttoJournal.mqh -- 4 actionDesc literals + 1 trigger label rewritten

  COttoJournal.mqh -- ProjectedTarget() anchor KEPT on the far edge (Decision B)

NOT PROVEN HERE

  Behaviour. No Strategy Tester run accompanies this commit. The probe set is
  static source analysis; the compile gate proves the tree BUILDS, not that the
  strategy performs. Four consequences are UNMEASURED:

    1. THE STOP NOW SITS INSIDE THE ZONE for the common case. With
       slDist = blockHeight + 0.5*ATR and the entry 1.0*ATR past the far edge,
       the stop lands 0.5*ATR inside the zone whenever ATR < 2*blockHeight --
       i.e. for most real zones. It is no longer protected by a zone boundary,
       so a wick that respects the structural level can now take the trade out.
       This is the direct, accepted cost of clause 1 and it is DOCUMENTED AT THE
       SL DEFINITION rather than left to be discovered. If it proves costly in
       the tester, the fix is a decision about slDist (and therefore about lot
       sizing), NOT a quiet re-anchor of the stop.
    2. TRADE FREQUENCY WILL FALL. A setup whose entry is already crossed is now
       refused instead of armed. On a fast instrument the entry sits one full
       ATR beyond the far edge, so a zone that gets run through before the next
       tick is skipped entirely. The magnitude is unmeasured.
    3. ROUTE A IS NOW DEAD FOR THE SHIPPED STYLE. ENTRY_FRONT_EDGE can never
       satisfy priceValid, so every live entry is a virtual arm fired by
       CheckVirtualTriggers(). That is intentional, but it means a
       comment/structure regression in the virtual engine now has no physical
       fallback behind it for the default configuration.
    4. Broker STOPS_LEVEL interaction is untested. The stop is 0.5*ATR inside
       the zone and the entry 1.0*ATR outside it; on a broker with a wide
       STOPS_LEVEL the SL->entry distance is unchanged (still slDist) so
       ValidateStopDistance should be unaffected, but no live terminal verified
       it.
