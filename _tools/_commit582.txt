582: fix -- the physical route rests a BUY_STOP/SELL_STOP, not a pullback-fill limit

RATIONALE

  The requested entry geometry -- "breakout anticipation": entry BEYOND the far
  S/R edge, SL on the OPPOSITE edge, market-on-cross trigger -- was already the
  geometry this tree computes. Verified line by line, not assumed:

    COttoBlockManager.mqh  BlockEntryPrice()          LONG -> b.bottom + slDist
                                                      SHORT -> b.top    - slDist
    COttoOrderManager.mqh  CalcEntryPrice()           same mapping
    COttoOrderManager.mqh  CalcSLDistance()           blockHeight + 0.5*ATR
    COttoOrderManager.mqh  stopLoss                   entry -/+ slDist (opposite edge)
    COttoOrderManager.mqh  CheckVirtualTriggers()     ask < trigger (LONG) /
                                                      bid > trigger (SHORT) -> MARKET deal

  With slDist = blockHeight + 0.5*ATR those collapse to LONG entry = b.top +
  0.5*ATR and SHORT entry = b.bottom - 0.5*ATR: 0.5*ATR BEYOND the far edge,
  with the SL a full slDist back on the opposite edge. The trigger is a genuine
  CROSS (price must RISE into a LONG, FALL into a SHORT) and the fill is a
  trade action DEAL, so it is already market-on-cross and not a resting touch.

  So no arithmetic was rewritten. The defect was in the OTHER route.

THE DEFECT

  PlaceOrArmOrder() is a hybrid router. CheckVirtualTriggers() (the virtual arm)
  was already correct. The PHYSICAL branch was not, and it contradicted itself:

    COttoOrderManager.mqh  GetOrderTypeForBlock()  -> ORDER_TYPE_BUY_LIMIT /
                                                      ORDER_TYPE_SELL_LIMIT
    COttoOrderManager.mqh  priceValid (LONG)       -> entryPrice < GetBid() - boundary

  For a LONG the entry is b.top + 0.5*ATR, i.e. ABOVE the market. That is never
  a legal BUY_LIMIT, and `entryPrice < Bid` is FALSE on a fresh setup -- so a
  clean setup could not rest physically at all. The test flipped TRUE only once
  price had already run THROUGH the far edge by more than the boundary, and in
  exactly that state a BUY_LIMIT rests BELOW market and fills on a PULLBACK back
  into the zone.

  That is the reversion/pullback trap the anticipation model exists to replace,
  with no breakout confirmation anywhere in the path. The SL was still one
  slDist away, so the R:R arithmetic looked intact and the defect was invisible
  in the risk numbers -- only the ENTRY SEMANTICS were inverted: to get filled
  the market had to move AGAINST the breakout. The in-tree comment already
  described the intended behaviour ("a buy-stop above resistance"), so the route
  contradicted its own documentation.
SOURCE

  COttoOrderManager.mqh -- GetOrderTypeForBlock(), 2 lines
    The producer, and the whole behavioural fix:

      - return (GetDirectionForBlock(block) == DIR_LONG) ? ORDER_TYPE_BUY_LIMIT
      -                                                  : ORDER_TYPE_SELL_LIMIT;
      + return (GetDirectionForBlock(block) == DIR_LONG) ? ORDER_TYPE_BUY_STOP
      +                                                  : ORDER_TYPE_SELL_STOP;

    A STOP can legally rest 0.5*ATR beyond the far edge, and only a STOP is
    reached by price moving IN the breakout direction. Both routes now carry
    identical trigger semantics: price must CROSS the level to fire.

  COttoOrderManager.mqh -- priceValid, 2 comparisons inverted
    Must mirror the type above, and be measured against the side each stop
    triggers on (Ask for a buy, Bid for a sell):

      - if(isLong) priceValid = (entryPrice < GetBid() - boundary);
      - else       priceValid = (entryPrice > GetAsk() + boundary);
      + if(isLong) priceValid = (entryPrice > GetAsk() + boundary);
      + else       priceValid = (entryPrice < GetBid() - boundary);

    Now the physical rest can ONLY happen while the entry is still AHEAD of
    price, which is precisely the state a stop needs. A setup whose entry has
    already been reached falls through to the virtual arm and fires as a MARKET
    deal on the cross -- the same economics, strictly more likely to fill.

  COttoOrderManager.mqh -- SendOrderWithRetry(), re-quote branches REMOVED
    The BUY_LIMIT -> SnapToTick(GetBid()) / SELL_LIMIT -> SnapToTick(GetAsk())
    retry arms were both dead (no pending caller sends a limit now) and wrong:
    dragging a BUY_STOP DOWN onto the Bid is the exact mirror of the v5.30
    [Invalid price] bug this block was written to fix. A stop now resends its
    geometric entry verbatim, and if the venue keeps refusing it the caller's
    virtual fallback arms the setup. Only true MARKET orders are re-priced to the
    executable side -- that logic is untouched.

    Deliberately NOT replaced with a stop-side re-quote: a legal re-quote would
    still silently relocate the entry away from the far-edge geometry the setup
    was armed at, converting a stop-style fill back into a pullback fill. The
    entry price is a strategy invariant here, not a fallback to be negotiated.

DEFECT CLASS CLOSED

  The same polarity bug existed in two places and only one was ever fixed. v5.30
  corrected "never move a LIMIT onto the wrong side of the market" in the RETRY
  path; the ROUTE DECISION itself still assumed limit semantics. This release
  fixes the decision, which is the one that determines whether a trade is a
  breakout or a fade.

  minimum and trade a rejection for an invalid stop. Rejecting the setup instead
  is a strategy decision, not part of this fix.
