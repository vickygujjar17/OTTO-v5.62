568: initial risk allocation halved across all four rungs; journal gains standalone block-height / 1R-distance / risk-allocation rows

RATIONALE

  Two requests, one release: the operator wanted the initial risk cut in half,
  and wanted the journal to show the block geometry, the entry and the money
  actually at stake without reading the chart.

RISK -- the ladder halved as ONE piece

  RiskPercent is a `const` (terminal-override lock), so halving it alone would
  have left T2 still risking MORE than the initial entry. The whole ladder
  moved together, preserving its flat-head shape and every ratio between rungs:

      rung                     trigger           v5.67     v5.68
      T1  RiskPercent          at market          1.0%  ->  0.5%
      T2  InpRiskT2Pct         +1.0R              1.0%  ->  0.5%
      T3  InpRiskT3Pct         +2.0R              0.5%  ->  0.25%
      T4  InpRiskT4Pct         +3.0R              0.25% ->  0.125%
                                               --------     --------
      summed stacked exposure                  2.75%   ->  1.375%

  Only LOTS and MONEY change. Every scale-in trigger, breakeven floor, profit
  lock and ATR-trail rung is an R-multiple of the primary's own 1R, so no price
  level moves and no milestone re-times. The trade manager's m_halfRiskTriggers
  is an R-TRAIL milestone despite the name and was deliberately NOT touched.

  No formula changed. GetRiskMoney(), CalculateLotSize() and RiskPctLotSize()
  all read RiskPercent / the InpRiskT* knobs dynamically at call time, so a
  default edit flows through with no other code change. Verified, not assumed.

DELIBERATELY NOT HALVED

  SafetyMaxRiskPct stays 1.5%. It is a per-leg ABORT escape hatch enforced by
  CHighTableAuditor::AuditRiskExposure(), not a budget that tracks tuned risk.
  Halving it would pin the auditor's ceiling at 0.75% and start flagging
  ordinary normalized lot sizes. The peak single leg is now 0.5%, so the
  tolerance band WIDENS from 1.5x to 3x -- the safe direction.

  Consequence to report, not absorb: a halved target means the v5.49 below-min
  abort fires more often on small accounts. It still never clamps up to a fixed
  lot, so the failure mode remains "no trade", not "oversized trade".


JOURNAL -- additive rows only

  v5.57 already printed Top/Bottom/Mid/Height. v5.68 ADDS, in both writers:

      Block Height      price AND pips, with the "= Top - Bottom" derivation
      SL Distance (1R)  price AND pips, with the "= Block Height + 0.5*ATR"
      Risk Allocation   the % knob AND its dollar value on live equity

  LogEntry() additionally prints the REALIZED fill-to-SL distance beside the
  planned 1R, so a slipped fill is now visible instead of hiding behind the
  planned number -- and that is what finally CONSUMES riskDist, which was
  computed at the top of LogEntry() and then thrown away. The wick rows gained
  an "Anchor=" field (SFractalPeak.price: the pivot high/low, distinct from the
  candle's full H/L, which were already printed).

  FmtPips() had zero call sites before this release. It is now the formatter
  behind every pips value above, via seven calls.

  Two new private helpers, both equity-guarded so a journal row can never print
  a divide-by-zero artefact:
      RiskMoneyAt(pct)   equity * pct / 100
      RiskPctTail(money) "  (= 0.50% of equity)" for a committed dollar figure

STRUCTURE CONSTRAINT (why the rows are ADDITIVE)

  _probe/test_v557_frontrun.py:576 requires the substring

      " | Mid=" + FmtPrice(blk.midpoint) + " | Height=" + FmtPrice(blk.blockHeight)

  to appear EXACTLY TWICE. Block Height therefore went into its OWN row rather
  than extending the combined row, which would have made the count 4 and red-
  lined a passing probe. Same reason the enriched wick rows REPLACE the old
  ones in place rather than being added beside them -- test_v557:589 pins the
  wick guard to exactly two occurrences.
