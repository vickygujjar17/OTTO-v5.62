566: primary timeframe -- structure, ATR and the bar gate now run on M15 instead of the chart period

RATIONALE

  Until now the EA had NO timeframe parameter. All 70 timeframe call sites
  read PERIOD_CURRENT, which resolves to whatever period the chart the EA is
  attached to happens to use. The same .set file therefore produced different
  structure on an H1 chart and an M15 chart, and the ATR that sets stop
  distance scaled with the chart rather than with the strategy.

  This commit makes the strategy period explicit and pins it to M15.

  THIS IS A BEHAVIOUR CHANGE, NOT A CONFIG CHANGE. It is listed here because
  the arithmetic is not cosmetic:

    - slDist = blockHeight + 0.5 * ATR now reads M15 ATR instead of H1 ATR.
      ATR(14) on M15 is roughly a quarter of ATR(14) on H1, so the 0.5*ATR
      term shrinks, stops tighten, and risk-based lots grow for the same
      risk percent.

    - Bar-count inputs silently re-base, because they are now counted in
      M15 bars rather than chart bars:
          MaxBlockDistance = 150  ->  ~6.25 days on H1,  ~37.5 h on M15
          LookbackBars     = 300  ->  ~12.5 days on H1,  ~75 h on M15

  Existing .set files need no edit: the input DID NOT EXIST before, so no
  saved value is orphaned. Anyone who wanted the old chart-following
  behaviour can set InpPrimaryTF to the period they used to run.

METHOD

  Every content edit was made BYTE-LEVEL (open 'rb' / open 'wb'), not through
  a text-mode round trip. otto.mq5 carries 10 mojibake em-dash sequences
  (c3 a2 e2 82 ac e2 80 9d) and OttoDefines.mqh carries real ones; a
  text-mode write with the wrong codec re-encodes them and corrupts the tree
  further. The new comment lines in otto.mq5 were inserted ABOVE the mojibake
  banner and never reconstructed it. Verified after the fact: strict UTF-8
  decode succeeds on all 9 sources, mojibake count still exactly 10, zero
  U+FFFD introduced, no BOM, no bare LF.

  Note the working tree is CRLF while the index stores LF (core.autocrlf), so
  git diff must be read with that in mind: a byte-level write that preserves
  the working-tree CRLF does not produce a whole-file rewrite in the diff.
